## 1. 项目概述

### 1.1 项目背景

Notepad++ 是 Windows 平台常用的轻量级文本 / 代码编辑器，具备启动快、体积小、功能密度高等优势。但它的界面风格、交互体验、主题体系和部分现代化能力已经显得陈旧。

**Textlume** 的目标不是做一个完整 VS Code 替代品，而是做一个更现代、更美观、更顺手的轻量级编辑器：

- 比系统记事本强大；
- 比 VS Code 更轻；
- 比 Notepad++ 更现代；
- 优先服务快速编辑、代码查看、日志查看、文本处理等高频场景。

### 1.2 核心目标

| 目标 | 说明 |
|------|------|
| 🎯 高频功能覆盖 | v1.0 覆盖 Notepad++ 高频核心功能，而不是一次性追求 95% 全量能力 |
| ✨ UI 现代化 | 暗色主题、高分屏支持、清晰布局、现代交互 |
| ⚡ 快速稳定 | 启动快、输入低延迟、文件读写可靠 |
| 🪶 轻量级 | 优先控制安装包体积、运行内存和后台资源占用 |
| 🧩 可扩展 | 先做命令系统和内部扩展点，再逐步演进插件系统 |
| 🛡 数据安全 | 文件保存、外部变更、崩溃恢复要避免用户数据丢失 |

### 1.3 目标用户

- Notepad++ 现有用户：需要更现代的替代品。
- 开发者：需要快速编辑代码、查看日志、处理配置文件。
- 普通用户：需要一个比记事本强大、比 VS Code 轻量的工具。
- 文本处理用户：需要批量搜索、替换、行处理、格式化等能力。

## 2. 产品边界与版本策略

### 2.1 v1.0 核心边界

v1.0 目标是做出一个稳定可用的轻量级编辑器，而不是一次性完成所有高级功能。

v1.0 必须包含：

| 模块 | v1.0 范围 |
|------|-----------|
| 文件 | 新建、打开、保存、另存为、最近文件 |
| 标签页 | 多标签、新建、关闭、切换、未保存状态提示 |
| 编辑器 | 语法高亮、行号、括号匹配、自动缩进、基础代码折叠 |
| 查找替换 | 当前文件查找、替换、正则、大小写匹配 |
| 文本处理 | 大小写转换、删除空行、行排序、基础 JSON 格式化 |
| 编码与行尾 | UTF-8/UTF-8 BOM/UTF-16/GBK 基础检测，LF/CRLF 转换 |
| 主题 | 暗色 / 亮色主题，基础主题切换 |
| 会话 | 恢复上次打开的文件列表和窗口状态 |
| 安全 | 外部文件修改提示、保存失败保护、崩溃恢复草稿 |

### 2.2 v1.0 暂不追求的内容

以下内容可以设计接口，但不作为 v1.0 阻塞项：

| 功能 | 建议版本 | 原因 |
|------|----------|------|
| 完整插件市场 | v2.0 | 需要权限、安全、分发、更新体系 |
| QuickJS 插件运行时 | v1.1 / v2.0 | 复杂度高，容易拖慢主线 |
| 宏录制与回放 | v1.1 | 依赖命令系统稳定 |
| Git 集成 | v1.2 / 插件 | 容易膨胀为 IDE 能力 |
| 内置终端 | v2.0 / 插件 | 不符合轻量核心定位 |
| 完整大文件编辑 | v1.x 持续优化 | CodeMirror 对超大文档有限制，需要分阶段实现 |
| 跨平台深度适配 | v1.x 后续 | 第一阶段以 Windows 为主 |

### 2.3 版本演进建议

| 版本 | 定位 |
|------|------|
| v0.1 | 可运行骨架：窗口、编辑器、打开保存、基础标签页 |
| v0.2 | 可日常使用：查找替换、语法高亮、主题、最近文件 |
| v0.3 | 稳定性增强：编码、行尾、会话恢复、外部修改提示 |
| v0.4 | 文本处理增强：行操作、格式化、批量处理 |
| v0.5 | 性能增强：大文件查看模式、流式搜索、内存优化 |
| v1.0 | 稳定正式版：可靠、轻量、文档完善、安装包可发布 |
| v1.1+ | 命令面板、宏、插件原型、高级扩展能力 |

## 3. 技术架构

### 3.1 技术选型

| 层级 | 技术选择 | 理由 | 风险说明 |
|------|----------|------|----------|
| 桌面框架 | Tauri 2.x | 比 Electron 更轻，Rust 后端适合文件、搜索、系统能力 | Tauri 插件生态和部分窗口能力需要实测 |
| 前端框架 | React 18 + TypeScript | 生态成熟，组件化清晰，适合复杂 UI | 注意避免状态过度分散 |
| 编辑器核心 | CodeMirror 6 | 现代、模块化、扩展性强、适合轻量编辑器 | 超大文件完整编辑能力有限 |
| 样式方案 | Tailwind CSS | 开发快，主题系统易维护 | shadcn/ui 组件需按需引入，避免包体膨胀 |
| 状态管理 | Zustand | 轻量、易拆分、TS 友好 | 需要定义清晰 store 边界 |
| 构建工具 | Vite | 快速开发体验，适合 Tauri 前端 | 生产构建需关注资源体积 |
| 图标库 | Lucide Icons | 风格统一、轻量 | 按需引入 |
| Rust 编码处理 | encoding_rs + BOM 检测 | 支持常用编码转换 | 自动识别不可能 100% 准确，需要 UI 提示 |
| Rust 搜索 | regex / ignore / walkdir | 适合多文件搜索和 glob 过滤 | 与 JS RegExp 语义不同，需要说明 |

### 3.4 架构原则

1. **文件真实状态由 Document Manager 管理**，不要让 UI 组件直接管理文件路径、编码、脏状态。
2. **菜单、工具栏、快捷键、命令面板统一走 Command Registry**，避免后续功能分散。
3. **Rust 负责文件系统、编码、多文件搜索、文件监听、恢复数据落盘**。
4. **前端负责编辑状态、交互、CodeMirror 扩展组合和 UI 展示**。
5. **大文件必须进入降级模式**，不能简单把所有内容塞进 CodeMirror。
6. **插件系统后置**，先保证内部命令系统稳定。

## 6. 大文件处理策略

### 6.1 关键原则

Rust 可以流式读取大文件，但 CodeMirror 6 并不适合无条件完整加载超大文件。因此 Textlume 必须区分文件大小并采用不同模式。

### 6.2 文件大小分档

| 文件大小 | 模式 | 策略 |
|----------|------|------|
| < 10MB | normal-edit | 正常编辑，启用语法高亮、折叠、搜索、撤销 |
| 10MB - 100MB | large-edit | 降级编辑，关闭 minimap、复杂高亮、部分折叠，限制撤销历史 |
| > 100MB | large-readonly | 优先只读查看，分页 / 分块加载，搜索走 Rust 流式搜索 |
| 二进制文件 | binary-preview | 不进入文本编辑器，提示二进制或十六进制预览后续支持 |

### 6.3 大文件模式限制

大文件模式默认：

- 关闭 Minimap；
- 关闭复杂语法高亮或只启用纯文本；
- 关闭代码折叠；
- 限制撤销历史；
- 限制全文装载；
- 搜索尽量走 Rust 后端；
- 状态栏明确显示“大文件模式”。

### 6.4 v1.0 可接受目标

v1.0 不承诺完整流畅编辑任意 100MB+ 文件。

v1.0 目标建议：

| 场景 | 验收标准 |
|------|----------|
| 打开 1MB 文本 | 秒开，正常编辑 |
| 打开 10MB 文本 | 可编辑，输入无明显卡顿 |
| 打开 50MB 日志 | 可查看，可搜索，功能降级但不崩溃 |
| 打开 100MB+ 日志 | 进入大文件查看模式，不假死，不无提示崩溃 |

## 7. 编码、行尾与文件变更策略

### 7.1 编码检测流程

```text
打开文件
  │
  ├─ 检测 BOM
  │    ├─ UTF-8 BOM
  │    ├─ UTF-16 LE
  │    └─ UTF-16 BE
  │
  ├─ 无 BOM 时自动猜测
  │    ├─ UTF-8
  │    ├─ GBK
  │    ├─ Latin-1
  │    └─ unknown
  │
  ├─ 解码成功
  │    └─ 返回 content + detectedEncoding
  │
  └─ 解码不确定 / 失败
       └─ 提示用户选择编码或以只读方式打开
```

### 7.2 保存策略

保存时默认保留：

- 原始编码；
- 原始行尾；
- 是否带 BOM；
- 文件路径和修改时间元数据。

用户显式执行“编码转换”时，才改变编码。

### 7.3 行尾策略

行尾是独立于编码的文档属性。

| 操作 | 行为 |
|------|------|
| 打开文件 | 自动检测主要行尾类型 |
| 新建文件 | 使用设置中的默认行尾 |
| 保存文件 | 默认保留当前文档行尾 |
| 转换行尾 | 用户主动执行 LF / CRLF / CR 转换 |

### 7.4 外部文件修改策略

```text
外部文件变化
  │
  ├─ 当前文档未修改
  │    ├─ 自动重新加载，或
  │    └─ 提示用户重新加载
  │
  ├─ 当前文档已修改
  │    └─ 弹窗提示：
  │        1. 保留我的修改
  │        2. 从磁盘重新加载
  │        3. 另存为新文件
  │
  └─ 文件被删除
       └─ 提示：保留缓冲区 / 关闭标签
```

### 7.5 崩溃恢复策略

- 未保存内容定期写入 recovery 草稿目录；
- 草稿只保存必要信息：内容、原路径、编码、行尾、时间戳；
- 正常关闭时清理已保存文档草稿；
- 异常退出后下次启动提示恢复；
- 恢复出来的文档默认标记为 dirty，避免误以为已保存。

## 8. 命令、菜单与快捷键系统

### 8.1 设计原则

Textlume 的菜单、工具栏按钮、快捷键、命令面板、未来宏系统和插件系统都应基于统一命令系统。

不要在 UI 组件里直接写业务动作。

### 8.2 Command Registry

```ts
interface TextlumeCommand {
  id: string;
  title: string;
  category: string;
  enabled?: () => boolean;
  visible?: () => boolean;
  run: (...args: unknown[]) => Promise<void> | void;
}
```

示例命令：

```ts
registerCommand({
  id: 'file.open',
  title: '打开文件',
  category: 'File',
  run: async () => {
    await documentActions.openFile();
  },
});
```

### 8.3 快捷键系统

```ts
interface Keybinding {
  commandId: string;
  key: string;
  when?: string;
}
```

示例：

| 快捷键 | 命令 |
|--------|------|
| Ctrl+N | file.new |
| Ctrl+O | file.open |
| Ctrl+S | file.save |
| Ctrl+Shift+S | file.saveAs |
| Ctrl+F | search.find |
| Ctrl+H | search.replace |
| Ctrl+W | tab.close |
| Ctrl+Tab | tab.next |

### 8.4 菜单与工具栏

菜单和工具栏只引用 commandId：

```ts
interface MenuItem {
  commandId: string;
  group?: string;
  order?: number;
}
```

这样未来插件或宏系统只需要注册命令，不需要侵入 UI。

## 9. UI/UX 设计

### 9.1 设计原则

1. **编辑优先**：界面服务于内容，不要让视觉效果影响输入性能。

## 10. 数据流设计

### 10.1 文件打开流程

```text
用户操作：打开文件
  │
  ▼
React UI
  │
  ▼
Command Registry: file.open
  │
  ▼
Document Manager
  │
  ▼
Tauri IPC: open_file(path)
  │
  ▼
Rust Backend
  ├─ 获取文件元数据
  ├─ 判断文件大小
  ├─ 检测 BOM / 编码
  ├─ 解码内容
  ├─ 检测行尾
  └─ 返回 content + metadata + recommendedMode
  │
  ▼
Document Store 创建 OpenDocument
  │
  ▼
CodeMirror 根据模式加载内容
  │
  ▼
状态栏显示编码、行尾、语言、文件大小
```

### 10.2 文件保存流程

```text
用户操作：保存
  │
  ▼
Command Registry: file.save
  │
  ▼
Document Manager 检查文档状态
  │
  ├─ Untitled → 走另存为
  ├─ 外部已修改 → 提示冲突
  └─ 正常保存
  │
  ▼
Tauri IPC: save_file(payload)
  │
  ▼
Rust Backend
  ├─ 按指定编码编码文本
  ├─ 按指定行尾转换
  ├─ 写入临时文件
  ├─ 原子替换目标文件
  └─ 返回新修改时间
  │
  ▼
前端更新 isDirty=false、lastSavedAt、lastKnownModifiedAt
```

### 10.3 当前文件搜索流程

```text
用户输入搜索词
  │
  ▼
Find Panel
  │
  ▼
CodeMirror Search Extension
  │
  ├─ 高亮所有匹配
  ├─ 显示匹配数量
  └─ 支持上一个 / 下一个
```

### 10.4 多文件搜索流程

```text
用户执行多文件搜索
  │
  ▼
Search Panel
  │
  ▼
Tauri IPC: search_in_files(query, root, include, exclude)
  │
  ▼
Rust Search Engine
  ├─ 遍历目录
  ├─ 应用 ignore / glob 规则
  ├─ 跳过二进制和超大不适合文件
  ├─ Rust regex 搜索
  └─ 返回匹配文件、行号、上下文
  │
  ▼
Search Result Panel
  │
  └─ 双击结果 → 打开文件并跳转
```

### 10.5 崩溃恢复流程

```text
文档内容变化
  │
  ▼
Debounce 触发 recovery 保存
  │
  ▼
Rust 写入 recovery 草稿
  │
  ▼
应用正常关闭
  ├─ 已保存文档：清理草稿
  └─ 未保存文档：保留草稿

下次启动
  │
  ▼
检查 recovery 目录
  │
  ├─ 无草稿：正常启动
  └─ 有草稿：提示恢复
```

## 11. 插件系统设计

### 11.1 插件系统定位

插件系统是 Textlume 的长期扩展方向，但不应成为 v1.0 主线阻塞项。

正确演进顺序：

1. **v1.0：内部命令系统**

4. **v2.0：完整插件系统**

## 14. 技术风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |

## 结论

Textlume 的推荐实施路线是：

1. 先做一个稳定、轻量、好看的文本 / 代码编辑器；
2. 把文件保存、编码、行尾、外部修改、恢复机制做好；
3. 用 Command Registry 统一菜单、快捷键和工具栏；
4. 对大文件采用分档和降级策略，不做不现实承诺；
5. 插件系统后置，等核心架构稳定后再扩展。

这样可以避免项目一开始就变成“轻量版 VS Code”，也能更稳定地向 Notepad++ 替代品方向演进。
